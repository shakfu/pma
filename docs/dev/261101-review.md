# pma usability and speed-of-use review

2026-11-01, against `538d9c4`. Question: is working through `pma tui` or `pma web` faster than running an agent by hand in a terminal, and where do the keys, the commands and the display cost time?

Evidence:

- **M**: measured. CLI times with `time`; web server times with `curl` against `pma web` on the real store; page times in headless Chromium over DevTools (`scratchpad/web-timing.mjs`); flow times from `runs` and `jobs`. 10 runs and 25 jobs, one user.

- **C**: read from the code, not run.

- **E**: estimate.

The speed review of this morning (below) covered the dispatch pipeline. Its S1, S5, S7 and the per-project locks are built: the last two interactive dispatches took 1 and 4 s from key to agent (M, jobs 22 and 23 against runs 9 and 10). This review covers what is left: the front ends.

**Status, same day:** U1, U2 (all four parts), U3, U4, U5 and U6 are built, with U7's Enter, confirmations and double load; see `CHANGELOG.md` Unreleased. Not built: U7's log tail, which needs a cache of the tool count by offset. Measured after: a `j` on the web matrix is 33 ms (was 146). Found on the way: `pma review 9`, a run in the `margo` clone, takes 0.65 s against 0.10 s for a run elsewhere, which the TUI's one thread waits on when its detail opens; the `tree` and `diff` calls on that clone are the likely cost, not measured.

## Verdict

- **The machinery is fast enough.** Every read the front ends make is under 20 ms on the server, and the TUI's first frame needs one 6 ms query (M). Nothing below is a performance bug in the core.

- **The loop still has a dead end a person meets.** A hand-committed interactive run was settled without ticking its item, the item was dispatched again, the agent made no change, and the run now sits in the inbox offering a push that fails every time (M, runs 8 and 9, job 24).

- **Review is the slow human step and the TUI makes it slower than `git diff | less`.** The diff scrolls one line a key and 20 a page, with no end key and no search (C). Median ready-to-decided is 256 s (M).

- **Getting to the work costs more keys than it should.** The inbox lists 3 of 1,268 open items, because 8 carry `#agent` or `#manual` and all 113 projects are untiered (M). The way in is projects, scroll up to 113 rows, Enter, scroll up to 36 rows, then a key. No list has a filter.

- **The web is instant everywhere but the matrix**, where 1,272 rows cost 146 ms a key and are rebuilt every 2 s while an agent runs (M).

## 2. Findings

### U1. A run that changed nothing is offered for publication, and its item stays open (M)

Run 8 (`I margo:9`) was committed by hand and settled to `pushed` by the hand-commit rule (CHANGELOG, Fixed). Nothing ticked `margo:9`, so the project view still lists it as open 166 days. 55 s later run 9 dispatched the same item with `D`. The agent read the code, found the work in `HEAD`, changed nothing, and the run reached `ready` with `no changes`, verify passed, $0.38, 46 s. `D` saw this and left it: job 22's log ends "waits in `pma review`: the run changed nothing; the base already passed, so no check discriminates this change". `u` approved it and queued `pma push 9`, which failed in 1 s: "nothing to stage: no changes". The inbox still shows `#9 approved to publish`, `u` on it fails again, and the only way out is `X`.

Three defects, in order of cost:

- A run settled from a hand commit does not tick its item, so the task is re-listed and re-dispatched.

- A run with an empty diff and a summary saying the work is done is treated like any ready run. `screen::next_act` offers approve, then push.

- The inbox row shows nothing of job 24's failure. The run's `error` field holds it; `pma review 9` prints it; no list does.

**Fix:** when a run settles to `pushed` from a hand commit, tick its item if the item's text is unchanged, as `stage` does, and say so in the notice. A ready run with `no changes` offers `X` as its next act, with a `what` cell of "no changes: close", and `D` and `u` refuse it with that reason. A run whose last publish job failed shows `error` in its row's `what` cell. Each is small; the first removes the cause.

### U2. Reaching a project, and acting on a set of them (M, C)

Header: "113 projects, 113 untiered ranked as tier 5". 8 of 1,268 open items carry `#agent` or `#manual`, so "Ready for agents" has 3 rows and "Tasks for you" none. The work is reached through `2`, up to 113 `j`, Enter, up to 36 `j`, then `I` or `d`. By hand that is `cd <project>`, `claude`, and pasting the item: about the same number of keystrokes (E).

Your direction, 2026-11-01: tiering is one way of subdividing; you also want to pick a project by fuzzy search, to tag projects into categories, and to apply a run or a workflow to a tagged set. What exists today:

- **Tags.** 2 tags on 8 projects (`ai` 3, `audio` 5; M). `--tag` selects on `pma run`, `workflow run`, `scan`, `sync` and `dispatch`. In the front ends `e` sets `tag +name` on one project and its view lists its tags. The projects tab has no tag column, no view filters by tag, and `f` (start workflow) parses no `--tag` and sends `tag: None` (`screen.rs:2434-2465`) while the CLI takes it. `z` over marked projects covers a set marked by hand.

- **Name.** The web's sidebar filters projects by substring. No TUI table filters; `Mode::Choose` has `/` (`tui.rs:537`). The CLI's `pma dispatch <project>` and `project show` take a name typed in full.

- **Scope.** `Tab::query` passes `Selection::default()` (`keys.rs:66`), so every tab always shows every project. The CLI's `--tag` and project arguments have no counterpart in the TUI or web.

- **Movement.** PageUp and PageDown are mapped by `key_name` and bound to nothing in a list, so they do nothing (C, `keys.rs`).

**Fix,** four parts, all shared between `App` and `app.js` through `pma-core`:

1. **Jump.** `O` on any tab opens a fuzzy chooser over every project's name and tags (subsequence match, best score first, as `Choose` filters today but fuzzy); Enter opens the project view. Two keys and a few letters from anywhere, which is the `cd` of working by hand.

2. **Filter and mark.** `/` on any table filters its rows by the same fuzzy match over the row's cells; the projects tab gains a `tags` column so `/audio` keeps the five. `*` marks every row the filter keeps, so a set is `/audio`, `*`, `z`. PageDown and PageUp move by the pane's visible rows.

3. **Scope.** `#` offers the tags in a `Choose` list plus "all"; the choice fills every tab's `Selection.tags`, the header says `scope: audio`, and `c`, `d`, `z`, `f` and `U` act within it. This is the front-end form of `--tag`. `Tab::query` takes a `Selection` instead of building the default.

4. **Sets in typed lines.** `f` and `z` accept `--tag=<t>` as the CLI does, and the scope's tag is the default target when no project is named. `e` on marked projects sets a tier or a tag on all of them.

Tiering stays as it is, one axis among these. Parts 1 and 2 are the smallest and remove most of the keystrokes above; part 3 is the one that changes the API.

### U3. Reading a diff in the TUI is slower than a pager (C, M)

`Mode::Detail` scrolls by 1 on `j`, by 20 on PageDown whatever the height, and has no key to the end, no search and no jump between files or sections (`tui.rs:446-453`). A 300-line diff is 15 pages. `git diff | less` has `G`, `/`, `n` and half pages. Ready-to-decided is the largest human step (median 256 s, M), and the web's detail is already a plain scrollable region with the browser's find.

**Fix:** PageDown and PageUp by the viewport height; `G` and End to the bottom. Then `v` on a run opens its diff in `$PAGER` (default `less -R`) with the TUI suspended, and the TUI resumes on exit; one key, the tool already in the terminal. `v` is bound to tasks only, so a run binding passes the one-meaning test. The detail's diff comes from `dispatch::diff`, which the pager can take as text.

### U4. The footer lists 23 hints for a ready run (C)

On the inbox with a ready run selected, the footer lists 11 acts that fit the run, open, open project and mark, 7 acts that need no row, `?` and `q`: about 340 characters, 3 lines at 120 columns and 5 at 80 (`App::footer`, `fold`). The body loses those lines, and the one hint that matters, the next act, is first but surrounded.

**Fix:** the footer shows the row's acts, next act first, then `?` for the rest. The acts that need no row (scan, sync, note, run, check PRs, approve clean, push approved) are the same on every row and belong in `?`. The web already does this with More.

### U5. Some acts block the TUI (C)

`api::command_line` returns `None` for approve, reject, close, merge, stop, notes and settings, so they run on the UI thread (`api.rs:2252-2284`). Of these:

- `RejectRun` takes the project lock, waiting up to 2 s, then runs git to revert the attempt.

- `MergePr` runs `gh pr merge`, a network call with no timeout (earlier review, R2-M20).

- `TakeOver` and `FocusPane` call herdr's socket.

The loop draws "Working..." first and then takes no key and polls no change until the act returns.

**Fix:** queue `MergePr` as a job, since `pma merge <id>` exists and the job list already shows the outcome; it is the one act that can take seconds. The general fix, acts on a worker thread with the loop still drawing, is worth doing only if a second act turns out to block for long.

### U6. The web matrix rebuilds 20,000 nodes a key and every 2 s (M, C)

`draw()` replaces the whole content on every key and every refresh (`app.js:408-531`). On the matrix that is 1,272 rows and 20,441 nodes: 146 ms a `j`, 53 ms a `load()`, and 750 KB of JSON a refresh. While a job runs, the refresh is every 2 s, `tr.scrollIntoView` pulls the view back to the selected row, and a focused button loses focus. The inbox and projects are 1 to 3 ms and do not show this.

**Fix:** on Down and Up, change `aria-selected` on two rows and redraw the toolbar; do not rebuild tables. Call `scrollIntoView` from a key, never from a refresh. Skip the redraw when the screen JSON is byte-equal to the last one, which is the common case of a tick. Then the matrix is the only tab that needs more, and `quadrant_limit` with a "show all" toggle, as the CLI already caps it, covers that.

### U7. Smaller items

- **Double load at start (M).** `restore()` loads the tab and the project list; the first `tick` arrives at once and `refresh()` loads both again. Skip `refresh()` on the first tick.

- **Enter on a task opens its project, not the task (C).** In the inbox and the matrix, the task's description, which is what the agent is given, is two navigations away. Enter should open the task everywhere; `o` already opens the project.

- **Confirmations that guard nothing (C).** `s` (stage; `git reset` undoes it) and `T` (take over; opens a pane) each ask `y`. `d`, `x`, `u`, `p`, `M`, `R`, `b`, `U` and `D` spend money or publish and should keep theirs.

- **Agent logs are re-read whole every 2 s (C).** `watch::agents` reads and parses each running agent's log on every inbox, activity and project refresh, in the TUI, the web server and its event thread (`watch.rs:106-128`). A long session's `stream-json` log is megabytes. Read the tail, and cache the tool count by offset.

- **The detail clones the screen every frame (C).** `render` clones `self.screens[t]` and `self.mode` each draw (`tui.rs:842,867`), which for a detail is the whole diff. At one frame a second this is nothing; on a long diff with held `j` it is a copy a key. Borrow instead of clone when it shows.

- **`pma report` median key to agent, 44 s (M).** Most of the 8 runs are from before S1. The figure will settle on its own; a date-bounded report option would show it now.

## 4. Recommended order

1. **U1.** Tick the item on a hand-commit settle; a no-change run closes rather than publishes; a failed publish shows on the row. Removes the one dead end a person met this week.

2. **U2 parts 1 and 2.** `O` to jump to a project by fuzzy name or tag; `/` to filter any table, `*` to mark what it keeps, a `tags` column, page keys. Then Enter opens a task (U7). This is the direction you gave; it is also the largest keystroke saving.

3. **U3.** PageDown by height, `G`, and `v` to a pager. Review is the longest human step.

4. **U2 parts 3 and 4.** The `#` scope and `--tag` in `f` and `z`. Needs `Tab::query` to take a `Selection`; do it after parts 1 and 2 show which sets you actually form.

5. **U4 and the two confirmations of U7.** Footer density and `s`, `T`. Small, each a few lines in `keys.rs` and `App::footer`.

6. **U6.** Selection without rebuild, no scroll on refresh, skip equal screens. The matrix is unusable while an agent runs; the other tabs are fine.

7. **U5.** Queue merge. The rest of the blocking acts are sub-second until shown otherwise.

8. **U7's log tail and double load.** Low.

## 5. Alternative framing

The findings above read the inbox as the home screen and fix its paths. The evidence reads the other way: 8 tagged items in 1,268, and the last five dispatches all came from a project view or by target. If the project view is the product, then the fix is one key from anywhere to a project by name (`O`), Enter opening the task, and the inbox becoming what it is, a strip of runs waiting on you. Your answer on selection points this way, and the order in section 4 already follows it. The open question it leaves: should the inbox's task panes go, or show the tasks of the current scope?

A budget to test either against: a key answers within 50 ms in the TUI and 100 ms in the web; a refresh never moves the selection, the scroll or the focus; no row offers an act that is known to fail. U1, U6 and the double load each break one of these today.

## pma speed review

2026-11-01, against `4074db5` plus the uncommitted refresh work. Question: is `pma` faster to use than running an agent by hand, and what stops dispatch being immediate?

Evidence:

- **M**: measured from your store (`runs`, `attempts`, `jobs`, `verify_base`) and job logs. 8 runs and 21 jobs, one user, so the numbers show where time goes and are not statistics. Times have one-second resolution.

- **C**: read from the code, not run. A fixture to time the blocking cases was not run.

- **E**: my estimate.

**Status, same day:** S1, S2, S3, S5, S6 (off by default), S7 and S8 are built, with the timings of section 5 in `pma report`. S4's key for `--worktree` is not. None of it has run on a real project yet, so the "after" column below is expected, not measured.

### Verdict

- **`I` is slower than doing it by hand.** Recorded key-to-agent times are 6, 52 and 44 s (M). By hand, `cd` plus `claude "<task>"` takes about 10 to 20 s of typing (E). pma's work is a baseline test run the person at the keyboard does not use.

- **`d` costs 42 to 75 s before the agent starts** (M), but runs unattended, so it costs less than `I`.

- **The queue is the larger problem.** One job runs at a time, and a global lock is held for a run's whole life. One `I` stopped all other work for up to 8005 s (M).

- **Most elapsed time comes after the agent finishes.** Run 4: 393 s from key to ready, then 5059 s to pushed (M). Removing the baseline wait alone would not change this.

### 2. Findings

#### S1. `I` runs a baseline nobody reads (M, C)

`attempt` starts after `prepare`, and `prepare` runs base verify first (`dispatch.rs:981`). Its result feeds the acceptance gates (`accept.rs:121`), and for an interactive run a person is the judge.

**Fix:** skip base verify when `pick.interactive`. The run then shows "the base was not verified" at review. **Gain:** 44 s to about 1 s on `margo`.

#### S2. One job at a time, and one lock across all projects (C, M)

- The runner claims one job and waits for it (`jobs.rs:102`).

- `run_dispatch` holds `session.lock` until it returns (`main.rs:2198`), through the agent and any `I`.

- Commit, push, reject, close and rework take the same lock (`main.rs:4262`, `api.rs:1621`, `main.rs:2928`).

- `Session::acquire` waits 2 s, then errors (`store.rs:925`). The TUI runs reject in place (`tui.rs:1776`), so `x` should freeze for 2 s and then fail while any agent runs. Read from the code, not run.

So work on `margo` blocks a push on `pma`. `max_parallel` (2) applies only inside one job (`dispatch.rs:1362`), so two separate `d` presses run one after the other.

**Fix:** lock per clone, and run jobs for different projects at once, up to `max_parallel`. **Constraint:** `fail_interrupted_runs` marks every queued or running run failed, and is safe only because the global lock proves no other session lives (`store.rs:3162`). Each run needs its own liveness record first, such as a pid, or a live run gets marked failed. This is the largest change here, and the one that most moves the queue.

**Smaller first step:** let interactive runs bypass the runner, each in its own process, so an `I` never holds the queue. It still needs the liveness record.

#### S3. A job that cannot run waits its turn to say so (M, C)

`clone_busy` is checked when the job starts (`dispatch.rs:640`), after it has queued. You pressed `d`, waited 292 s, and got a refusal for a state that was true at the keypress.

**Fix:** check at the keypress and refuse at once, or better, keep the job queued until the clone is free. Refusing is the small change. Waiting is the one that serves "move the queue".

#### S4. One finished run blocks the next task in a project (C, M)

A clone holds one run until it is published or rejected (`dispatch.rs:640`). `--worktree` avoids that, at the cost of a fresh checkout with no build cache. Bundling (Space, then `d`) is the current way round it. Jobs 8 and 10 both failed on this.

**Fix:** S3's waiting job covers the common case. Offer `--worktree` in the refusal as a key.

#### S5. Two of three `I` runs ended in a dead end (M)

Runs 6 and 7 changed `HEAD` during or just after the session: you committed `4b3adfd` 51 s after run 6 was ready, and `66a576d` landed 20 s before run 7 was ready. `pma push` then refused (`publish.rs:215`), jobs 15 and 18 failed, and both runs ended with `pma close`. Committing yourself is normal in an interactive session, so pma adds steps here and no value.

**Fix:** at the end of an interactive run, or at `u`, if the work is already in `HEAD` and the tree is clean, mark the run finished with no further step. Refusing stays right for a headless run.

#### S6. `d` blocks on the baseline too (M, C)

Base verify takes 13 to 23% of the job (42 of 184 s, 75 of 393 s). The gates need it for headless runs (`accept.rs:121`), so it cannot be dropped, but the agent need not wait.

**Fix:** start the agent at once and run base verify in parallel in a private checkout of the base. `verify-trees` already exists for this (`dispatch.rs:1850`). **Costs:** two test suites at once, port or file clashes in projects whose tests use fixed ones, and a cold build unless the tree is kept between runs. `features.verify_seconds` must come from the last recorded value. Try it behind a config key.

**Alternative:** verify the top listed tasks' projects while idle, so `d` hits the cache (`dispatch.rs:1782`). No concurrency risk, but it spends CPU on runs that may not happen, and a dirty clone probably misses, since the key is a commit built from the working tree (`dispatch.rs:907`; inferred).

#### S7. Nothing says why it is waiting (C)

Between `I` and the pane, the footer says only that a job was queued. A silent 44 s looks like a hang, and invites a second key press.

**Fix:** "verifying base, about 43 s" from the recorded time, and the job's position if it is queued. Small, and worth doing even after S1, for `d`.

#### S8. Smaller items

- **`gh` workflow name bug (M).** `dispatch.rs:1165` passes a name, and `nanosrv` has two matching files. `scan.rs:958` already passes an id. Failed job 17.

- **`I` confirm (C).** `I` is `Ask::Confirm` (`keys.rs:582`). It publishes nothing and spends no budget through pma. Drop the `y`.

- **`sync --apply` shows as failed (M).** Jobs 5 and 20 exit failed because some projects were skipped, such as disabled issues. Job 20 made 0 changes. A skip should not raise a failure notice.

- **README timing (M).** It says a scan of 95 repositories takes about 15 s. Your scans took 35 to 149 s, 61 s most recently, with 112 projects.

### 3. Compared with working by hand

| Action | By hand | pma now | pma after S1, S2, S5 |
|-|-|-|-|
| Start one interactive agent | 10 to 20 s typing (E) | 2 keys, then 6 to 52 s | 1 key, about 1 s |
| Start a second task elsewhere | a new terminal, same again | waits for the first to end | 1 key, about 1 s |
| Find the task | read a `TODO.md` | already listed | same |
| Unattended run with verification | you write the script | `d y`, then verified | same, starts sooner with S6 |
| Finish after you committed yourself | nothing | a refused push, then `pma close` | nothing |
| See every project's state | 112 checks | one screen | same |

pma already wins on finding work, on unattended runs and on the overview. It loses on starting an interactive agent and on doing two things at once, which are the cases a person notices most.

### 4. Recommended order

1. **S1**, skip the baseline for `I`. Small, and removes the largest single delay you see.

2. **S8**, the `gh` id and the `I` confirm. Each a few lines.

3. **S5**, finish interactive runs already committed.

4. **S3**, refuse at the keypress, then wait instead.

5. **S7**, say why it is waiting.

6. **S2**, per-clone locks and parallel jobs, liveness record first. Needs a design note, since it changes what makes a run safe to fail.

7. **S6**, behind a config key, once S2 shows how much concurrency the machine takes.

### 5. Alternative framing

The target above is "reduce each delay". The other way to put it is a budget: **key to agent under 2 s, and nothing a person presses is refused after a wait.** Base verify, log fetches and locks then become work that must fit around the agent. That turns S1, S3 and S6 into one rule, and it can be tested.

`pma report` already holds the data. Adding key-to-agent, ready-to-decided and decided-to-pushed medians would show whether each change helped. `jobs.created_at`, `runs.dispatched_at`, `ready_at`, `decided_at` and `published_at` exist. I would add this before S2, so the large change has a before and an after.

### 2. High

**R2-H1. Publish pushes the agent's intermediate commits, which review never showed.** C.

- **Where:** `src/publish.rs:124-134`. `checkout -B <branch> approved_head` keeps every commit since `base`.

- **What review shows:** `pma review` shows only the net diff against `base`. It does not show commit messages or authors.

- **Scenario:** the agent commits a file in one commit and deletes it in the next. `~/.ssh` is readable, as `README.md:52` says, so the file could be a key. The net diff is clean, and approval is allowed; `review_reasons` notes only "the agent committed". `pma push` or `pma pr` then puts the file into the remote history.

- **Fix:** publish one commit, built from `approved_tree` on `base` with `git commit-tree`. Never push the ancestry of `approved_head`. The 0.5.0 CHANGELOG kept `git commit` so that user hooks run. That is still possible: check out `base`, `read-tree` the approved tree, then `git commit`.

**R2-H2. A workflow plan id does not bind the plan to an instance, a target, the unit data or the parameters.** C.

- **Where:** `Plan::id` (`src/pass.rs:187-206`) hashes node, unit ids, agent and model.

- **Why ids repeat:** root unit ids are always `u1..uN` (`src/pass.rs:318`), and minted ids are `node-K`. The same graph over the same number of units gives the same id in any project or instance.

- **Scenario:** `pma workflow run review projA --dry-run` prints plan `X`. `pma workflow run review projB --approve X` then creates an instance on `projB` and runs agents there.
  - The same holds for `--instance 6 --approve <id printed for instance 5>`.

  - It also holds for a different `--set`: the prompt text changes and the id does not.

- **Contract broken:** README "Repeating work".

- **Related gaps, C:**
  - The plan's worker and model come from `taken[0]` alone (`src/pass.rs:562`). `stage` resolves each batch at its own project's tier (`src/pass.rs:1960`).

  - An `edit` node under a policy shows `by route`. A route activated between print and approve keeps the id.

- **Fix:** hash the instance id, the unit data, the arguments, the prompt text, `agent_budget` and each unit's resolved worker. A stronger option stores the printed plan as rows, approves it by row id, and executes the stored rows instead of re-deriving them.

**R2-H3. `make check` fails at HEAD on the author's platform.** C. See section 1. v0.6.0 shipped with this test failing on macOS. There is no CI (`.github/workflows` is absent), so nothing ran the suite on Linux either.

### 3. Medium

#### Publish and the git boundary

The README states the boundary: "this stops an accidental push, not a determined one" (`README.md:52`). The agent process runs unconfined (`src/dispatch.rs:1143`). The `claude` worker may run the verify command through Bash (`src/worker.rs:356`). So a hostile agent can write anywhere the user can. R2-M1 to R2-M4 matter only for that agent; they are Medium for that reason. R2-M5 and R2-M6 need no hostile agent.

- **R2-M1. `refs/replace/*` swaps the approved tree at publish.** C, by a repro using the same git calls as `pma`.
  - The snapshot does not cover refs, and no call sets `GIT_NO_REPLACE_OBJECTS`.

  - `git replace H E` keeps the reviewed tree id `H`. `read-tree --reset -u H` (`src/publish.rs:135`) then checks out `E`, and that tree is pushed.

  - Fix: add `--no-replace-objects` to every `wt_git` call.

- **R2-M2. The snapshot misses `extensions.worktreeConfig` with a per-worktree `core.worktree`.** C, by repro.
  - Where: `runs_or_redirects`, `src/dispatch.rs:387-417`.

  - Effect: `git add --all` in review then reads another directory. Publish's `checkout --force` writes the tree into that directory.

- **R2-M3. Global and XDG git config and `~/.ssh/config` are outside the snapshot** (`src/dispatch.rs:327`). I.
  - An added `core.sshCommand`, `insteadOf` rule or filter runs under the credentialed fetch and push.

  - Alternative: run publish's git with `GIT_CONFIG_GLOBAL` set to a copy taken at dispatch.

- **R2-M4. `<commondir>/info/attributes` can mark a file `-diff`, so review prints "Binary files differ"** (`src/dispatch.rs:1460`). I.
  - Fix: run the review diff with `--text --no-textconv --no-ext-diff`.

- **R2-M5. A relative `core.hooksPath` (husky's `.husky`) resolves in the worktree for the snapshot and in the clone for `clone_held`.** C, by repro.
  - Where: `src/dispatch.rs:339-342` against `:267` and `:1544`.

  - Scenario: editing a tracked `.husky/pre-commit` fails the run with `GIT_CHANGED`. The clone then stays held until `--keep-git-changes`.

- **R2-M6. A false "already pushed" discards approved work.** C.
  - Where: `src/publish.rs:110-116`.

  - If the worktree's `HEAD` is moved to an upstream commit after approval, the run is marked `pushed` and nothing is pushed.

  - `remove_worktree` then deletes the work.

- **R2-M7. With `sandbox off`, the publish-time verify can move `HEAD` before the push** (`src/publish.rs:174-224`). C.
  - Nothing compares `HEAD^{tree}` with the tree verify started from.

  - `README.md:213` recommends `sandbox off` for some projects.

#### Concurrency

- **R2-M8. `publish::settle` writes the whole run row with no state guard and no lock.** C.
  - Where: `src/publish.rs:277-321`.

  - Plain `pma review` reaches it, after one untimed `gh pr view` per run.

  - Scenario: `pma review 7 --minutes 10` during a slow settle is overwritten.

- **R2-M9. Writers that hold the lock still write the full row** (`src/publish.rs:53,66`, `src/dispatch.rs:1557,1606`, `src/pass.rs:2198`). C.
  - `pma push 7` reads the run, runs verify for minutes, then writes back `review_seconds` and `reviewed_tree` from its copy.

  - The 0.6.0 change made `--minutes` column-scoped but did not change these writers. The 0.6.0 approve guard checks only `state`.

  - Fix: write only the columns a step owns. Do this instead of adding more state guards.

- **R2-M10. `pma review N` and `--approve` run `git add --all` in the run's worktree without the lock, even while the run is `running`** (`src/main.rs:2236-2242`, `src/dispatch.rs:1461-1471`). I.
  - Risks: `index.lock` failures, or an index the agent or publish did not expect.

#### Workflow engine

- **R2-M11. The `todo` sink's dedupe and tick compare `normal_text(item)`, which keeps trailing tokens, with the parsed text, which strips them.** C, found by two reviewers.
  - Where: `src/pass.rs:1650-1680`.

  - Scenario: a sink item `"{title} #agent"` never matches its own earlier write.
    - A resumed pass inserts a duplicate.

    - `check_duplicates` (`src/todo.rs:802`) makes it a lint error.

    - Every later sink, dispatch and prune on that file is then refused.

  - Fix: run the sink text through the parser, and refuse token-only text.

- **R2-M12. A rule map wider than its `max_units` reports `Capped`, but `--cap max_units=<n>` cannot raise the limit** (`src/pass.rs:1023-1034`, `src/main.rs:3112`). C.
  - `raise_caps` changes the instance caps, not the node's width.

  - The instance stays capped. `stop` is the only way out.

- **R2-M13. The plan ceiling omits route escalation and resets `batch_budget` per `execute` call** (`src/pass.rs:538,569`, `src/dispatch.rs:1000`). I.
  - An escalating edit can cost 2 x `agent_budget`. A plan with a map and an edit can exceed both the printed total and `batch_budget`.

  - `agent_budget 0` is accepted and prints `<= $0.00`.

- **R2-M14. A tick or remove is written to `TODO.md` before its SQLite transaction commits** (`src/pass.rs:1688`). I.
  - After a crash between the two, the resumed pass finds "no open item" and records the unit as failed.

- **R2-M15. Errors inside `stage` use `?` after earlier batches have created worktrees and `Running` rows** (`src/pass.rs:2005,2038`). C.
  - `git worktree prune` is never called, so git keeps records of the removed directories.

- **R2-M16. A short Rhai script can hang `workflow check` or `propose` for hours** (`src/script.rs:302-315`). C, measured.
  - Each `Graph::stage` deep-clones the graph to check for duplicate names, and `Graph` is passed by value. A graph of N nodes therefore costs O(N^2) in native code, which `MAX_OPERATIONS` does not count.

  - Measured: 10,000 nodes took 23 s and 20,000 took 116 s.

  - The author writes the script, so this mostly hurts the author.

#### Scope

**Other ways to read the project.** These are inferences, not measurements.

1. **The product is the queue and the publish path, and the engine is an experiment.** Freeze the engine. Ship only the linear review, confirm, note graph from the pilot. A ~50-line script could run that graph. Revisit the engine once the 20-item pilot clears the bar.

2. **The approval guarantee needs a stored plan, not a recomputed hash.** Each planned feature (retry, laps, parallelism) widens what `Plan::id` must cover. Nothing tests that coverage. Storing the plan rows removes the problem.

3. **The boundary is an unconfined agent plus a git snapshot.** R2-M1 to R2-M4 show the snapshot will keep needing new entries. The stated threat model accepts that. If untrusted tasks are a goal, the `sanduk` worker is the only boundary that holds. Consider making it the default for `--auto`.

### 7. Recommended order

1. Fix the macOS path in the test (R2-H3). Add Linux CI that runs `make check`.

2. Publish one commit from the approved tree (R2-H1).

3. Bind the plan id to the instance, target, data, arguments and prompt, or store plans (R2-H2).

4. Make run-row writes column-scoped (R2-M8, R2-M9).

5. Add timeouts to network calls under the lock (R2-M20).

6. Add `--no-replace-objects`, and diff with `--text --no-textconv --no-ext-diff` (R2-M1, R2-M4).

7. Normalise the `todo` sink text through the parser (R2-M11).

8. Finish the 20-item pilot before extending the workflow engine.
